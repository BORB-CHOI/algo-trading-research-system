# ADR-0021 — 주·월봉은 일봉으로 만들고, 매일 전수로 대조한다

- **상태:** 제안 (오너 승인 대기)
- **날짜:** 2026-08-28
- **관련:** ADR-0002(데이터 소스), ADR-0018(나무 = 주·월봉 정본 · 주문 창구),
  ADR-0006(수정주가 back-adjust)

---

## 무엇이 문제였나

### ① 주·월봉을 매일 전 종목 받느라 6분을 썼다

주봉·월봉은 그 주(달)가 끝날 때까지 값이 매일 바뀐다. 그래서 매 갱신마다 전 종목을
증권사에 다시 물었다. 실측 2026-08-28:

| 단계 | 콜 | 시간 |
|---|---|---|
| **주·월봉** | **5,140** | **358초 (6.0분)** |
| 거래원 | 2,873 | 297초 |
| 나무 봉 증분 | 373 | 87초 |
| 공시 | — | 60초 |
| 합계 | | **13.9분** |

**주·월봉이 전체 콜의 64%**였다. KIS 한도가 계정당 초당 20건이라, 이걸 두면 아무리
조여도 13분 밑으로 못 내려간다.

### ② 그런데 그렇게 받아 온 주·월봉의 1.59%가 이미 틀려 있었다

전 종목 4,310개·63만 봉을 일봉과 맞춰 보니 **1,339종목(31.1%)이 어긋났다.**

한화(000880) 2026년 8월 첫째 주:

| 어디 | 값 |
|---|---|
| 우리 주봉 파일 | **83,800** |
| 나무에 다시 물어본 값 | **100,600** |
| KIS 주봉 | 100,600 |
| 우리 일봉으로 만든 주봉 | 100,600 |

**저장된 주·월봉만 옛 수정주가 그대로 남아 있었다.** 일봉은 액면 변경 뒤 다시 받아
갱신됐는데 주·월봉이 안 따라갔다(일봉 표본 30종목 대조 → 30/30 최신).

지금까지 자가 검증은 **KIS 일봉 표본 20종목**만 봤다. 이 규모의 오류는 안 잡힌다.

## 무엇을 하기로 했나

### 1. 진행 중인 주·월봉은 일봉으로 만든다 — 증권사 호출 0

저장된 마지막 봉이 든 주(달)부터 다시 만든다. 그 봉은 받을 당시 진행 중이었을 수
있어서다. **그보다 과거는 한 줄도 안 건드린다.**

정본 규정은 그대로다 — 주·월봉의 정본은 **나무 수집본**이고, 여기서 바뀌는 건
"진행 중인 봉을 누가 채우나"뿐이다.

**같은 값이 나오는지 실측했다(2026-08-28):**

| 대조 | 결과 |
|---|---|
| 최신 주봉 200종목 | **200/200 완전 일치** |
| 최신 월봉 200종목 | 195/200 (틀린 5개도 저가 1원·거래량 2~5주) |
| 2024·2025·2026년 주봉 전체 | 99.4% · 98.9% · 99.2% |

틀리는 폭이 이미 오너가 수용한 "나무↔KIS 반올림 ±1원·거래량 몇 주"와 같은 수준이다
(ADR-0018).

### 2. 그 대신 매 회차 전 종목을 전수 대조한다 — 이것도 호출 0

일봉으로 주·월봉을 다시 만들어 저장본과 맞춘다. 실측 **4,310종목·63만 봉에 135.8초.**
### 2-1. 무엇을 "다르다"고 볼지 (오너 결정 2026-08-28)

| 항목 | 여유 | 왜 |
|---|---|---|
| 가격 4종 | **0원** | 1원만 달라도 다른 값이다 |
| 거래량 | **2주** | 나무가 자기 주봉과 자기 일봉을 1~2주 다르게 준다(중앙값 1주) |
| 거래대금 | 2주치 값어치 | 거래량 여유와 짝을 맞춘다 |
| 연말·연초에 걸친 주 | **뺀다** | 나무만 쪼갠다. KIS·화면 코드는 안 쪼갠다 — 규칙 차이지 오류가 아니다 |

이 기준을 넣기 전과 후 (전 종목 63만 봉 실측):

| | 어긋난 종목 | 어긋난 봉 |
|---|---|---|
| 여유 없이 | 1,335 | 6,943 (1.09%) |
| **기준 적용 후** | **55** | **274 (0.043%)** |

### 2-2. ⚠️ 남은 274봉은 다시 받아도 안 고쳐진다

주·월봉을 **전량 재수집한 뒤에도 그대로였다** — 나무 서버가 원래 그 값을 준다.
어긋난 종목을 KIS 로 심판 봤더니 **14건 전부 "일봉 합성이 맞고 나무 주봉이 틀리다"** 였다
(나무=KIS 0건). 예: 335870 은 나무 주봉만 정확히 5배 — 액면분할 미반영.

그래서 `VERIFY_REFETCH_CAP = 0` 으로 두고 **세기만 한다.** 고치려면 일봉으로 만든 값으로
덮어야 하는데 그건 "정본 = 나무 수집본"을 뒤집는 일이라 **오너 결정이 필요하다.**

⚠️ **대조가 알아내는 건 "둘이 다르다"까지다.** "어느 쪽이 맞다"는 증권사에 물어야 안다.

### 3. 창을 좁히는 건 이득이 없다 — 재보고 확인했다

| 대조 범위 | 대조한 봉 | 시간 (800종목) |
|---|---|---|
| 2026년~ | 30,758 | 21.6초 |
| 2024년~ | 107,749 | 24.8초 |

봉을 3.5배 더 봐도 15%밖에 안 늘어난다. 시간의 대부분이 **파일을 여는 데** 들어가기
때문이다. 그래서 창을 좁히는 대신 **파일을 덜 여는 쪽**으로 갔다(아래 4).

### 4. 곁들여 고친 것

| 고친 것 | 전 | 후 |
|---|---|---|
| KIS 호출마다 새 연결 → 줄기마다 이어 쓰기 | 콜당 통신 85ms | **17ms** |
| 파일 마지막 날짜를 매번 읽기 → 쪽지(`_last_dates.json`) | 2,000개 15.30초 | **0.16초** |
| 워터마크 갱신도 같은 쪽지 사용 | 주봉 폴더 7.70초 | **0.42초** |
| 수집기 상태 파일을 굵기마다 쓰기 → 5초에 한 번 | 6.9MB × 11,020회 | 시간당 몇 회 |

## 되돌리기

**한 종목 되돌리기 = 약 1.2초.** 전 종목이라도 나무로 62분, KIS로 8.6분이다.
코드는 예전 경로(`update_period_bars_kis`)를 지우지 않고 남겨 둔다 — 한 줄을 되돌리면
그대로 예전 방식으로 돌아간다.

## 안 바꾸는 것

- **주·월봉 정본 = 나무 수집본** (ADR-0018 그대로)
- 과거 봉은 갱신이 건드리지 않는다 — 어긋났을 때만 그 종목을 통째로 다시 받는다
- 상폐 종목을 데이터에서 빼지 않는다
- 화면 쪽 합성(`api/candles.py`)은 그대로 — 거기는 그리기용 표를 다루고,
  여기는 수집본 파일 형식을 다룬다. 묶는 규칙은 같다

## 남은 것

- 2023년 이전 주·월봉은 일봉과 30~39%만 맞는다. 이번 전량 재수집으로 고쳐지는지
  확인이 필요하다. 대조 시작점(`VERIFY_SINCE`)은 2024-01-01 로 두었다
- 수급·거래원의 줄기 수·간격은 아직 예전 값이다. 실측 표(초당 5.88 ~ 31.32)를
  오너에게 올렸고, **값은 오너가 고른다**
