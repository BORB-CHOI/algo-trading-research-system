# ADR-0005: 케이스 검사기 웹 도구 (시각 도구 아키텍처)

- **상태:** 수락 (1단계 = 캔들차트 슬라이스 완료)
- **날짜:** 2026-07-22
- **관련:** PROJECT_GUIDELINES §4.2(screening), §6.1(통계 검증), CLAUDE.md(매매 실행=결정론적 코드), BORB-31

## 맥락 (Context)

오너가 방향을 정했다. **"통상적인 전구간 백테스트"가 아니라**, 특정 종목·시점을 골라
**차트로 보고 → (조건검색식) 종목 선별 → 내가 정한 매매 전략을 얹어** "이 케이스가 어땠나"를
확인하는 **웹 도구**를 원한다. 순서: ① 차트 → ② 조건검색 종목 선별 → ③ 전략 오버레이.

이건 지침서가 세운 가드레일 백테스트(survivorship bias·point-in-time·train/test)와 **목적이 다르다**.
그건 *검증*이고, 이 도구는 *탐색·가설 생성*이다. 둘은 대체가 아니라 보완이다.

## 검토한 선택지 (Options)

**A. 파이썬 로컬 차트 (mplfinance/plotly).**
- 장점: 기존 파이썬 코드에 바로. 빠름.
- 단점: 인터랙션(줌·드래그·오버레이 조작)이 약하다. 오너가 원한 "웹"이 아니다.

**B. 웹 SPA (Vite + React + TypeScript) + FastAPI 백엔드.**  ← 채택
- 장점: **AI(작업자)가 가장 안정적으로 짜는 스택**. FastAPI 가 기존 파이썬 데이터 레이어
  (marcap 로더·exclusions)를 **단일 정본으로 재사용**. 인터랙션·확장(조건검색·오버레이) 용이.
- 단점: 순수 파이썬 리포에 JS/웹 스택이 추가된다(구조 변경). 새 의존성.
- 가드레일: 위반 없음. **웹은 그리기만**, 전략·매매 판단은 파이썬(결정론적)에 남긴다.

**C. Next.js.**
- 단점: App Router 등 프레임워크 고유 함정이 많고 이 용도엔 과하다(데이터는 어차피 파이썬 API).

## 결정 (Decision)

**B 채택.** `web/`(Vite+React+TS) + `api/`(FastAPI). 파이썬은 데이터·전략의 정본, 웹은 표현.

- **1단계(완료):** `GET /api/candles`(일봉 JSON, 거래대금 포함) + `GET /api/symbols`(종목 검색).
  `web/vite.config.ts` 가 `/api/*` 를 FastAPI(:8000)로 proxy.
- **차트 라이브러리 변천:** lightweight-charts → KLineChart core → **KLineChart Pro**(완성형 위젯).
  Pro 로 지표 메뉴 전체·이평선(기간 편집)·그리기 툴바(피보나치 등)·심볼 검색이 통째로 들어온다.
  거래대금(turnover)은 커스텀 지표로 등록해 메뉴에 노출. 상승=빨강/하락=파랑, 라이트 테마.
  **주의:** Pro 0.1.1 은 klinecharts v9 전용이라 klinecharts 를 v9 로 고정한다(Pro 유지 비용).
- **가드레일 못박기:** 이 서버·프런트는 BUY/SELL·포지션·주문을 하지 않는다. 전략 평가가 붙을 때도
  로직은 파이썬 layer3 에 두고 프런트는 결과만 그린다.
- **방법론 경계:** 케이스를 눈으로 본 결과는 **가설**이다. 검증이 아니다. 사후확신(이미 결과를 아는
  상태로 과거 차트를 보면 "됐겠네" 착각)을 막기 위해, 재생 기능을 붙일 땐 **미래 봉을 가리고 하루씩
  넘기는** 방식으로 설계한다. 돈을 걸기 전 검증은 여전히 가드레일 백테스트(BORB-31) 몫이다.

## 결과 (Consequences)

- 리포가 파이썬 단일 → **파이썬 + JS 모노레포**로 바뀐다. `docs/ARCHITECTURE.md` 갱신 필요(후속).
- 새 의존성: 파이썬 `webapp` optional group(fastapi·uvicorn·httpx), `web/` npm(react·vite·
  lightweight-charts). 프런트 산출물·node_modules 는 `.gitignore`.
- 실행: 백엔드 `uvicorn api.main:app --port 8000`, 프런트 `cd web && npm run dev`.

## 미해결 (Open questions)

1. **② 조건검색 종목 선별** — 증권사 조건검색을 참고한 선별 UI/로직. layer3 `screening.py`(placeholder)와
   어떻게 잇는가. 오너가 어떤 조건들을 넣을지.
2. **③ 전략 오버레이** — 오너가 정한 전략을 차트 위에 진입/청산 마커로 표시하는 방식. 전략 표현 포맷 미정.
3. **미래 봉 가림 재생 UX** — 사후확신 방지용 재생 모드 설계.
4. **데이터 로딩 성능** — 지금은 연도 parquet 를 `lru_cache` 로 캐시. 종목 인덱스/사전 집계가 필요할지.
5. **배포·실행 범위** — 로컬 전용인가, 나중에 어딘가 올리나. 인증 필요 여부.

## 개정 (2026-08-07) — KLineChart Pro(껍데기) 제거, 엔진 직접 사용

**배경.** 오너가 "차트에 봉 500개만 보이게" 를 원했다. 그런데 Pro 가 밖으로 내주는 기능은
`setSymbol / setPeriod / setTheme / setStyles / setLocale / setTimezone` 여섯뿐이고
**화면 범위·봉 개수를 다루는 것이 하나도 없다.** 안쪽 엔진(klinecharts)에는 `setBarSpace`·
`getVisibleRange`·`setOffsetRightDistance` 가 다 있는데 Pro 가 인스턴스를 감춰 밖에서 못 잡는다.

**검토한 대안.**

| | 500봉 | 지표·그리기 | 결론 |
|---|---|---|---|
| Pro 유지 + 안쪽 잡기 | 불가 | 유지 | 접근 경로가 없다 |
| **Pro 제거, 엔진 직접** | **가능** | **엔진에 이미 있다** (지표 25종·그리기 13종) | **채택** |
| lightweight-charts 로 교체 | 가능 | 전부 없음 — 다시 만들어야 | 손실이 크다 |
| TradingView Advanced Charts | 가능 | 전부 있음 | **라이선스상 불가** |

TradingView Advanced Charts 는 값은 무료지만 조건이 "공개 웹사이트에서만"이고
"공개 저장소에 라이브러리를 넣는 것 금지"다. 개인 백테스트 도구인 이 프로젝트는 대상이 아니다.
(오너가 신청서를 내보기로 했고, 승인되면 그때 다시 본다.)

**Pro 가 실제로 하던 일은 셋뿐이었다.** 데이터 받아오기 · 종목/주기 바꾸기 · 툴바 그리기.
지표도 그리기 도구도 전부 엔진 기능이고 Pro 는 그걸 **누르는 버튼**만 얹고 있었다.

**바뀐 것.**

- `ProChart.tsx` 가 `init(el, …)` 로 엔진을 직접 만든다. `@klinecharts/pro` 의존성 제거.
- 데이터는 `/api/candles` 를 직접 부른다(Pro Datafeed 규격 폐기).
- 위쪽 도구 막대를 우리가 그린다 — 주기(일/주/월) · **봉 개수(200/300/500/1000/전체)** ·
  보조지표(거래량·거래대금·MACD·RSI) · 그리기(피보나치·추세선·수평선·수직선·가격채널·사각형).
- 다시 그리기가 `chart.resize()` 로 정직해졌다. Pro 시절엔 window resize 이벤트를 쏘는
  우회가 필요했다(Pro 가 그것만 들어서).
- 봉 개수 맞추기(`fitBars`)는 봉 폭을 넣어 보고 실제로 몇 개 보이는지 되물어 보정한다.
  **오른쪽 여백을 재기 전에 없애야 한다** — 안 그러면 빈 공간이 자리를 먹어 500 을 넣었는데
  640 이 보인다(실측).

**같이 고친 것 두 개.**

1. **차트가 올해치만 나왔다.** `/api/candles` 는 `start` 를 안 주면 최근 1년만 준다(실측 144봉).
   Pro Datafeed 가 화면 구간에서 계산해 넘기던 값이라 Pro 를 벗으며 같이 사라졌다.
   이제 필요한 봉 수 + 지표 워밍업 250봉만큼 거슬러 계산해 넘긴다.
2. **거래정지일이 0원 캔들로 그려졌다.** marcap 은 정지일을 OHLC 0 · 거래량 0 으로 남긴다
   (BORB-32). 삼성전자 2018-04-30~05-03(액면분할 정지)이 주봉으로 합쳐지며 그 주 시가·저가가
   0 이 됐다. 전략 쪽(`surge._clean`)은 이미 걸러내고 있었고 화면만 안 걸렀다.
   `api.main.drop_halted` 로 같은 규칙을 적용했다(회귀 시험 추가).

**남은 것.** 종목 검색창은 안 만들었다 — 헤더 검색과 ①/③ 화면이 이미 종목을 밀어 넣는다.
차트 레이아웃 저장·리플레이 모드는 Pro 에도 없었다.

## 개정 (2026-08-08) — 기준일 = 화면 오른쪽 끝 봉

**배경.** 오너 요청: "기준일은 내가 차트 이동할 때 가장 오른쪽 끝에 해당하는 일봉으로."
날짜를 손으로 치고 차트를 따로 맞추는 게 아니라, **차트를 미는 것이 곧 과거로 가는 것**이다.
백테스트를 눈으로 훑는 방식과 맞는다 — 오른쪽 끝 = "이 시점까지만 안다" 이므로,
그 오른쪽은 어차피 서버가 안 본다(미래 데이터 훔쳐보기 금지).

**동작.** 양방향으로 묶었다.

- 차트를 밀거나 확대 → 오른쪽 끝 봉 날짜가 ③ 기준일 칸에 들어간다.
- 기준일 칸을 고치면 → 차트가 그 날짜를 오른쪽 끝에 두도록 옮긴다. 받아둔 것보다 과거면
  앞쪽을 더 받아온다. 휴장일을 넣으면 직전 거래일로 붙는다(서버 규칙과 같다).

**주·월봉도 그대로 된다.** 서버가 봉 날짜를 **그 주/달의 마지막 실제 거래일**로 실어 주기
때문이다(`api.main.resample_candles`). 주봉 하나의 오른쪽 끝 = 그 주 마지막 거래일 = 기준일.
분봉·틱이 생기면 `ProChart.INTRADAY_PERIODS` 에 주기를 넣는 것만으로 시각까지 붙는다 —
부르는 화면은 안 고쳐도 된다.

**엔진 함정 하나.** klinecharts 가 알려주는 "보이는 마지막 봉"(`getVisibleRange().to`)은
위치가 딱 떨어질 때 한 봉을 더 센다(`Math.round(위치 + 0.5)`). 평소 스크롤은 위치가 소수라
문제가 없고, 화면 끝에서는 잘려서 가려진다. 그런데 `scrollToDataIndex` 는 **항상 딱 떨어지게**
세워서 기준일이 하루 뒤로 밀렸다. 옮긴 뒤 봉 폭의 1%만큼 더 밀어 피한다(눈에 안 보인다).

**확인(브라우저 실측 2026-08-08).** 날짜를 넣었다 돌려받는 왕복이 정확히 일치했다
(2025-06-02 · 2024-11-15 · 2023-03-09 · 2026-08-04 — 마지막 하나는 받아둔 구간 밖이라
다시 받아오는 길을 탄다). 일요일 2025-06-01 → 2025-05-30. 월봉에서 밀면 2019-03-29(그 달
마지막 거래일), 주봉에서 밀면 2024-04-26(그 주 마지막 거래일). 기준일 2025-04-18 로
시뮬레이션을 돌리니 파동 구간이 2025-03-11~03-27 로 전부 기준일 왼쪽에 있었다.
