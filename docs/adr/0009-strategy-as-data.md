# ADR-0009: 전략·조건은 데이터로 정의한다 (보이지 않는 하드코딩 금지)

- **상태:** 수락
- **날짜:** 2026-07-24 (오너 지시)
- **관련:** BORB-42(전략 1호), ADR-0008(HTS UI), CLAUDE.md(placeholder 원칙)

## 맥락 (Context)

오너 지시: 전략과 그 전략이 쓰는 조건검색식은 **오너가 수동으로 추가한 것과 똑같이**
UI(조건검색·전략 패널)에 보여야 하고, 오너가 직접 수정할 수 있어야 한다.
**전략마다 보이지 않는 코드를 하드코딩하는 것 절대 금지.**

## 결정 (Decision)

1. **전략 = 카탈로그 + 파라미터.** 서버는 전략 목록을 조건검색과 같은 방식의 메타
   (이름·설명·파라미터 스키마)로 내려주고(GET /api/strategies), 모든 정량 값은
   요청 시 파라미터로 받는다. 서버 코드에 전략 숫자를 박지 않는다.
2. **종목 선별은 조건검색식을 그대로 쓴다.** 전략이 쓰는 선별 조건은 조건검색 UI 에서
   만든 조건식(A·B·C + AND/OR)과 동일한 데이터 형식으로 전달·저장한다.
   백테스트 러너도 같은 형식을 받는다 — 화면에서 보는 조건 = 백테스트가 쓰는 조건.
3. **파이썬 코드가 담당하는 것은 "계산 방법"뿐이다** (피보나치를 어떻게 긋는가,
   이평을 어떻게 구하는가). "어떤 숫자로"는 항상 데이터다.
4. 업계 표준 상수(피보나치 비율 0.236/0.382/0.5/0.618/0.786, 지표 정의 등)는
   계산 방법의 일부로 본다 — 단, 문서화하고 필요 시 파라미터로 승격한다.

## 결과 (Consequences)

- 기존 `case_overlay.py` 의 ma_cross(5/20 고정)도 이 원칙 위반 → 파라미터 노출로 개편.
- 오너가 UI 에서 손잡이를 돌리면 그 값이 곧 전략 정의가 되고, 저장된 전략(파라미터 묶음)이
  백테스트 입력으로 그대로 넘어간다. 코드 수정 없이 전략 변형 가능.
- 새 전략 추가 = 계산 함수 1개 + 파라미터 스키마 등록. 숨은 숫자가 생길 자리가 없다.
