# ADR-0009: 전략·조건은 데이터로 정의한다 (보이지 않는 하드코딩 금지)

- **상태:** 수락
- **날짜:** 2026-07-24 (오너 지시)
- **관련:** BORB-42(전략 1호), ADR-0008(HTS UI), CLAUDE.md(placeholder 원칙)

## 맥락 (Context)

오너 지시: 전략과 그 전략이 쓰는 조건검색식은 **오너가 수동으로 추가한 것과 똑같이**
UI(조건검색·전략 패널)에 보여야 하고, 오너가 직접 수정할 수 있어야 한다.
**전략마다 보이지 않는 코드를 하드코딩하는 것 절대 금지.**

## 결정 (Decision)

1. **전략 = 카탈로그 + 파라미터.** 서버는 전략 목록을 조건검색과 같은 방식의 메타
   (이름·설명·파라미터 스키마)로 내려주고(GET /api/strategies), 모든 정량 값은
   요청 시 파라미터로 받는다. 서버 코드에 전략 숫자를 박지 않는다.
2. **종목 선별은 조건검색식을 그대로 쓴다.** 전략이 쓰는 선별 조건은 조건검색 UI 에서
   만든 조건식(A·B·C + AND/OR)과 동일한 데이터 형식으로 전달·저장한다.
   백테스트 러너도 같은 형식을 받는다 — 화면에서 보는 조건 = 백테스트가 쓰는 조건.
3. **파이썬 코드가 담당하는 것은 "계산 방법"뿐이다** (피보나치를 어떻게 긋는가,
   이평을 어떻게 구하는가). "어떤 숫자로"는 항상 데이터다.
4. 업계 표준 상수(피보나치 비율 0.236/0.382/0.5/0.618/0.786, 지표 정의 등)는
   계산 방법의 일부로 본다 — 단, 문서화하고 필요 시 파라미터로 승격한다.

## 결과 (Consequences)

- 기존 `case_overlay.py` 의 ma_cross(5/20 고정)도 이 원칙 위반 → 파라미터 노출로 개편.
- 오너가 UI 에서 손잡이를 돌리면 그 값이 곧 전략 정의가 되고, 저장된 전략(파라미터 묶음)이
  백테스트 입력으로 그대로 넘어간다. 코드 수정 없이 전략 변형 가능.
- 새 전략 추가 = 계산 함수 1개 + 파라미터 스키마 등록. 숨은 숫자가 생길 자리가 없다.

## 개정 2026-08-03 — 주문 조건 스키마 확장

KIS "매수 주문조건 설정" 화면과 맞추기 위해 `Strategy.order` 에 두 필드를 추가했다.
둘 다 화면에서 입력·수정하는 값이며 서버 기본값은 없다.

- `credit: 'cash' | 'credit'` — 신용 구분
- `tick: number` — 감시 조건 도달가격의 ±N틱에 주문 (0 허용)

기존 저장본은 `toDraft()` 에서 `cash` / `0` 으로 읽는다(마이그레이션 불필요).
감시 유효기간은 KIS 제한과 같이 **최대 30일**로 검증한다.

## 개정 2026-08-03 (2) — 전략 화면 3단계 분리 (오너 지시)

오너 지적: "시세포착 감시와 가격기준 세부 설정, 매수 주문조건 설정을 왜 다 따로 뒀냐, 같은 건데."

전략 화면을 한 패널 안에서 3단계로 나눈다.

1. **① 종목선정** — 조건검색식을 **여러 개** 만들고 고친다. 저장소 `hts-screens`(신규).
   자주 쓰는 조건은 퀵칩으로 노출: 시가총액 · 거래대금 · **52주 신고가**(`new_high` 기간 250 ≈ 52주) ·
   주가범위 · 당일등락률 · 거래량 · 이평 위 · 골든크로스.
2. **② 매매전략** — ①에서 만든 검색식 하나를 골라 진입기법(피보나치 등)·시세포착 목표가·주문조건을 붙인다.
   저장소 `hts-strategies`. `Strategy.screen.name` 으로 어느 검색식에서 왔는지 남긴다.
3. **③ 감시** — ②를 특정 종목에 걸어둔 시세포착 감시 목록. 저장소 `hts-watchorders`.

**조건 0개 = 전체 종목.** 오너 질문("종목 선정을 안 하면 전체 선택인가")에 대한 답을 계약으로 못박았다.
`POST /api/screen/run` 이 빈 조건을 400 으로 막던 것을 풀고, 제외정책만 적용한 유니버스를 그대로 돌려준다.
화면에도 "조건이 없습니다 — 이대로 검색하면 전체 종목이 됩니다"를 띄운다.
응답에 `conditions`(적용 조건 수)와 `avg_chg`(검색된 종목의 당일 평균 등락률)를 추가했다 —
검색식이 오늘 얼마나 먹혔는지 한 줄로 보여주기 위함이다.

## 개정 2026-08-05 (3) — 감시 단계 제거, 전략은 2단계 (오너 지시)

오너: "시세포착 감시는 없애봐. 내가 생각하던 게 아니야." 감시 개념을 전부 뺀다.

1. **③ 감시 단계 삭제.** 저장소 `hts-watchorders`·`watchStore.ts` 도 제거. 전략은
   **① 조건검색식 + ② 매매전략** 2단계가 된다.
2. **② 의 `시세포착` 카드 삭제** — 목표가·목표가 기준(fib/round/manual)·근접 허용.
   주문조건에서도 감시 전제 필드를 뺐다: `도달가격의 N틱`, `설정기간`(감시 유효기간).
3. **저장 스키마 축소.** `entry` 는 `{key, params}` 만, `order` 는
   `{priceType, qtyType, qty, credit}` 만 남는다. `TargetKind` 타입 삭제.

**목표가 개념 자체가 사라진 게 아니다.** 성격이 바뀐다 — 사용자가 한 칸에 적는 값이 아니라
**진입 기법이 계산하는 값**이 된다. 전략 1호는 되돌림 레벨마다 분할 매수가를 여러 개 내므로
단일 목표가 입력칸으로는 애초에 담기지 않는다 (BORB-50).

ADR-0009 의 원칙(정량 값은 데이터로, 하드코딩 금지)은 그대로다. 바뀐 건 그 값을 **누가
만드느냐**다: 사람이 직접 넣던 목표가가, 사람이 넣은 파라미터로 기법이 계산하는 값이 됐다.
